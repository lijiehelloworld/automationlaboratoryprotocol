Automation Laboratory Language（ALL）覆盖从科学目标到设备执行和证据反馈的完整闭环。FSP 位于 ALL 内部，只负责设备能力和状态通信。架构图说明协议关系，不规定服务端内部部署方式。

<Note>工作站能力只分为对象、操作和系统三块。</Note>

## ALL 总体架构

![ALL 总体架构](/images/all-overall-architecture.png)

## 模块关系

1. FSP 从工作站读取对象、操作和系统定义，并负责状态读取、函数调用、异步任务和诊断。
2. 设备能力描述经过质量评估，通过后进入合格设备能力库。
3. 实验编排代理结合科学目标、研究对象状态和合格设备能力生成函数式实验方法。
4. 候选方法经过可计算性、状态闭合、物理约束仿真和科学语义评审。
5. 验证后的方法绑定具体工作站，转换为可下游执行的步骤和路径。
6. FSP 执行结果更新研究对象状态并形成证据和诊断反馈。

## 最小交互逻辑

```text
FSP 设备发现
  → 能力说明与质量准入
  → 研究对象状态上下文
  → 函数式实验方法生成与验证
  → 工作站绑定与 FSP 执行
  → 状态提交与证据反馈
```

## 模块输入输出

| 模块 | 输入 | 输出 |
| --- | --- | --- |
| FSP | 设备接口与当前状态 | 对象、操作、系统能力和执行结果 |
| 能力供给与准入 | FSP 能力数据 | 通过评估的自然语言与函数式能力 |
| 研究对象与状态 | 科学身份、样品、容器和状态 | 方法生成上下文 |
| 函数式实验方法 | 科学目标、上下文和合格能力 | 代码式方案和转换 JSON |
| 方法验证 | 代码式方案与同版本函数库 | 仿真报告、阻断诊断或通过结果 |
| 设备绑定与执行 | 验证后的方案 | 工作站步骤、路径、结果和状态变化 |
