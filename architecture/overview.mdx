## 大体交互逻辑

1. 调用方中的 ALP Client 发起能力发现请求。
2. ALP Server 返回 Manifest，描述设备模型和可用能力。
3. `read` 从状态管理读取当前值或事件，不经过驱动执行设备动作。
4. `write` 经执行与安全校验后写入设备，并把真实结果同步回状态管理。
5. `invoke` 根据设备模型中的动作定义执行动作，可返回同步结果或异步操作。
6. Physical Resource 统一管理作业对象和设备供给物料的实例、关系、状态与事件。
7. Workflow 和 Device Agent 只能组合已声明能力，不能绕过权限、安全校验或审计。

## 协议外部边界

从协议外部观察，调用方只依赖公开通信能力，不依赖服务内部模块如何部署：

```text
调用方中的 ALP Client
  → server/discover / devices/get_manifest
  → read / write / invoke / 可选方法
ALP Server
  → complete / input_required / operation / error
  → 可选事件
```

Device Model（设备模型）是静态能力声明，回答设备“能够提供什么”；State Management（状态管理）维护运行实例，回答设备“现在是什么状态”。Physical Resource 类型属于 Manifest，资源实例则通过运行时接口查询和修改。

Workflow 与 Device Agent 都是可选能力。Workflow 组合已声明 Action；Device Agent 在授权范围内选择 `read`、`write`、`invoke` 或 Workflow。两者都不能产生 Manifest 未声明的底层命令。
