## 接口目标

设备通过既有 API、SDK、RPC 或驱动被动接收调用。适配层把这些接口整理为 FSP 设备定义，并把 FSP 请求转换为设备实际调用。

```text
FSP 请求
  → 适配层映射
  → 设备接口被动执行
  → 返回实际状态、结果或诊断
```

设备不需要提供发现接口，也不负责生成实验程序。

## 三个说明维度

一项设备接口必须从三个维度说明完整事实：

| 维度 | 内容 |
| --- | --- |
| 操作 | 接口标识、用途、请求分类、参数、范围、枚举、前置条件、返回值和诊断 |
| 对象 | 适用容器的类型、形状、尺寸、材质、容积和允许状态 |
| 系统 | 设备可用状态、安全围栏、同步或异步模式以及结果验证 |

三个维度不是三条独立接口。一个加液 API 可以同时声明目标容器、加液参数、设备状态和异步执行方式。

## 加液接口示例

以下 HTTP 接口仅说明设备侧被动接口如何提供三方面事实：

```text
POST /operations/dispense
```

```json
{
  "request_id": "req-001",
  "target": {
    "container_id": "container-01",
    "container_type": "离心管",
    "expected_state": {"container_status": "无盖"}
  },
  "parameters": {
    "source_container_id": "source-01",
    "volume_mL": 0.5
  },
  "expected_device_state": "idle",
  "execution_mode": "async"
}
```

| 内容 | 维度 | 设备处理 |
| --- | --- | --- |
| `target` | 对象 | 确认容器存在、类型匹配、容量足够且状态为无盖 |
| `parameters` | 操作 | 校验来源、体积类型与范围并执行加液 |
| `expected_device_state`、`execution_mode` | 系统 | 检查设备空闲和安全围栏；需要时创建系统异步任务 |

```json
{
  "result_type": "task",
  "task": {
    "task_id": "task-001",
    "status": "queued",
    "cancellable": true
  },
  "diagnostics": []
}
```

任务完成后必须返回实际加液量、容器状态和诊断；不能把计划值当作执行结果。

## 最低要求

设备侧接口或映射层必须：

1. 为每项操作提供可映射的参数、对象和系统事实；
2. 被动响应 FSP 的读取、写入、调用和系统任务控制；
3. 在写入和物理动作前执行参数、状态与安全检查；
4. 返回实际结果或任务句柄；
5. 失败时保留可确认状态并返回结构化诊断。
