## 接口目标

设备接入的结果是：调用方可以通过设备接口明确知道设备能处理什么容器、能执行什么操作，以及当前是否允许执行。设备提供的是一组能力与控制接口；每项能力均应从对象、控制和系统三个方面完整说明。

```text
设备能力
├── 对象：本次能力作用的容器及其状态
├── 控制：接口动作、参数、约束和状态变化
└── 系统：设备可用性、运行状态和安全围栏
```

设备底层可以使用 HTTP、RPC、SDK 或设备协议实现；FSP 只规定对外返回的信息结构和行为，不规定内部 URL、驱动或通信帧格式。

## 三个能力方面

| 能力方面 | 要说明什么 | 主要作用 |
| --- | --- | --- |
| 对象 | `objects[]`：容器类型、形状、直径、材质、可观察状态和实例编号 | 说明能力作用于什么对象，以及对象当前处于什么状态 |
| 控制 | `operations[]`：操作标识、控制参数、类型、范围、枚举、前置条件、状态变化、返回值和诊断 | 说明如何调用设备能力以及成功后会发生什么 |
| 系统 | `system`：设备标识、能力修订号、可用状态、状态字段和安全围栏 | 判断当前是否允许调用，并保护设备不在不安全条件下执行 |

对象描述“操作谁”，控制描述“做什么”，系统描述“现在能不能做”。它们共同描述同一台设备已经提供的能力，不代表设备必须分别实现三套接口。

## FSP 能力获取

`fsp/discover` 与 `fsp/get_capabilities` 是 FSP 层必须提供的统一能力，不是单个设备必须原生暴露的接口。FSP 服务负责把一台设备提供或可映射的对象、控制和系统信息聚合为能力数据集，供调用方发现和读取。

```text
设备能力的对象、控制、系统信息
  → FSP 服务映射与聚合
  → fsp/get_capabilities
  → 调用方读取统一能力数据集
```

设备需要保证三方面信息真实、完整且可映射；FSP 服务必须负责 `device_id`、能力修订号、发现、条件读取和统一返回结构。能力获取的请求、响应和错误语义见[设备发现与能力数据集](/specification/fsp/capabilities)。

## 内容要求

### 对象信息

每个 `objects[]` 项必须至少包含 `object_type_id`、`variant_id`、`name`、`object_kind`、`properties` 和 `states`。容器的 `object_kind` 为 `container`；`properties` 必须按统一结构说明形状、长宽高、内外径、材质、标称容积、允许工作容积以及适用时的孔数和孔径，`states` 列出设备能够读取或改变的状态及允许值。完整目录和字段定义见[对象与容器](/specification/fsp/objects)。

例如，`container_status: ["有盖", "无盖"]` 表示设备能区分这两种容器状态，也为操作的前置条件提供可验证的依据。

### 控制信息

每个 `operations[]` 项必须至少包含 `command_id`、`command_class`、`execution_mode`、`parameters`、`initial_state`、`effects` 和 `returns`。参数必须给出名称、类型、是否必填、用途，以及适用时的范围、单位、枚举值或跨字段约束。

例如，`container_count` 的类型为 `int`、范围为 `1..10`，`container_ids` 受 `max(container_ids) <= container_count` 约束；服务端必须据此拒绝不符合已声明范围或跨字段约束的控制请求。

### 系统信息

`system` 必须说明设备可用状态、可读取的系统状态字段和安全围栏。安全围栏由服务端在执行前检查，例如“设备必须处于空闲状态”“容器必须无盖”或“参数不得超过物理上限”。调用方不能用自然语言说明覆盖安全围栏。

## FSP 状态读取

在执行控制操作前，调用方分别读取目标容器和设备系统状态。两个请求使用同一个 `device_id`，但读取的模块不同。

```json
{
  "jsonrpc": "2.0",
  "id": "read-object-1",
  "method": "fsp/read",
  "params": {
    "device_id": "2002186824385539",
    "category": "object",
    "object_ids": [1, 2]
  }
}
```

对象结果会返回容器编号、`container_status`、`sample_status`、体积和 `revision`；调用方据此确认 1、2 号进样瓶是否为无盖状态。随后读取系统：

```json
{
  "jsonrpc": "2.0",
  "id": "read-system-1",
  "method": "fsp/read",
  "params": {
    "device_id": "2002186824385539",
    "category": "system"
  }
}
```

系统结果中的 `state: "idle"` 与 `available: true` 表示设备当前可接收操作；`capability_revision` 和对象结果的 `revision` 用于后续并发检查。这样，读取接口同时给出对象和系统两类执行依据。

## FSP 操作调用

控制接口以能力数据集中已声明的 `command_id` 为准。下面的请求调用“加液”操作，并同时引用对象编号、操作参数和系统修订号。

```json
{
  "jsonrpc": "2.0",
  "id": "invoke-1",
  "method": "fsp/invoke",
  "params": {
    "device_id": "2002186824385539",
    "command_id": "add_liquid_with_material",
    "expected_revision": "12",
    "arguments": {
      "container_type": "进样瓶",
      "container_count": 2,
      "container_ids": [1, 2],
      "dispensing_plan": [
        {
          "sample_bottle_id": 1,
          "source_bottle": {
            "source_bottle_id": 1,
            "ingredient_name": "示例物料",
            "source_volume_mL": 0.5
          }
        }
      ]
    }
  }
}
```

| 请求内容 | 对应小模块 | 服务端要检查的内容 |
| --- | --- | --- |
| `container_type`、`container_ids` | 对象 | 类型和编号是否存在，且目标容器是否为无盖状态 |
| `command_id` 与 `arguments` | 操作 | 指令是否已声明；参数类型、范围和单位是否符合操作定义 |
| `expected_revision` | 系统 | 能力版本是否仍有效；设备是否空闲、可用且通过安全围栏 |

由于该操作声明为异步，成功接收后可先返回任务标识：

```json
{
  "result_type": "accepted",
  "value": {
    "task_id": "task-20260901-001",
    "state": "queued"
  },
  "diagnostics": []
}
```

调用方再使用异步任务接口读取进度、最终结果和诊断。任务成功后服务端提交实际对象状态；失败时不得伪造新的容器状态。

## 设备侧最低要求

设备侧服务或映射层必须：

1. 提供可稳定映射到 FSP `device_id` 的设备身份和能力版本信息；
2. 为每项设备能力提供或可映射对象、控制和系统三方面信息；
3. 允许 FSP 服务读取对象状态和系统状态，并返回修订号或观测时间；
4. 接受由 FSP 服务映射的已声明操作与参数；
5. 在执行控制操作前校验对象状态、参数约束和安全围栏；
6. 返回实际状态变化、异步任务结果或结构化诊断。

设备不需要原生实现发现或能力获取接口；只要对外满足以上信息与调用语义，FSP 服务即可将其纳入[技能提取](/specification/capability/overview)流程。
