## 目标

Automation Laboratory Language（ALL，自动化实验室语言）使实验意图能够转化为结构化、可计算、可验证并可由物理设备执行的实验方法，同时保留对象状态、执行结果、诊断、证据和来源。

## 组成

| 模块 | 主要职责 |
| --- | --- |
| 技能提取 | 从 FSP 完整技能定义生成设备技能描述，完成质量校验并进入合格设备技能库 |
| 函数式实验方法 | 将实验目标组织为可计算的函数调用，完成仿真、审查、设备绑定与执行计划生成 |
| 研究对象 | 统一表达样品、容器、状态、位置、证据和来源 |
| FSP | 发现设备，渐进披露技能定义，按风险分类提交请求并取得同步或异步结果 |

## 设备技能模型

设备通过多项技能接口表达自身能力。每项技能从三个维度说明：

```text
设备技能
├── 对象：该技能处理的容器、属性与状态
├── 控制：调用参数、请求分类、状态变化与返回值
└── 系统：所需设备状态、安全围栏与结果验证
```

## 角色

| 角色 | 职责 |
| --- | --- |
| 调用方 | 提出目标、选择能力、提交方法或操作、接收结果 |
| ALL 运行环境 | 组织技能准入、方法生成、验证、绑定和执行 |
| FSP 服务 | 提供统一远程设备通信接口 |
| 设备适配器 | 将 FSP 语义映射到设备已有接口 |
| 物理设备 | 执行操作并产生状态、结果和诊断 |

调用方中的协议客户端能力应集成在用户应用、自动化系统或智能体运行时内，不需要作为独立服务部署。

## 主交互

```text
发现设备
  → 读取技能摘要
  → 按需读取技能详情
  → 选择合格技能
  → 生成函数式候选方法
  → 仿真与审查
  → 绑定设备
  → 通过 FSP 提交分类请求
  → 接收结果、诊断、状态与证据
```

## 非目标

ALL 不规定设备固件、驱动实现、实验室调度算法、模型类型或厂商 API 形式，也不要求设备重写已有接口。
