---
title: "FSP 概述"
description: "ALL 内部面向设备通信的函数状态协议"
---

Function State Protocol（FSP，函数状态协议）是 ALL 内部的设备通信协议。它把不同 API、HTTP 服务或其他远程设备接口映射为统一的操作、对象和系统定义，使 ALL 语言引擎能够编译、仿真并执行设备调用。

FSP 不要求设备原生实现 FSP，也不规定设备内部代码结构。设备接入时，由适配层或部署配置提供 FSP 设备定义；运行时，FSP 只负责向已配置设备下发请求并返回状态、结果和诊断。

## 三个维度

对象、操作和系统是说明同一设备接口的三个维度，不是三类互不关联的接口。

| 维度 | 说明 |
| --- | --- |
| [操作](/specification/fsp/operations) | 具体接口做什么、如何调用、参数和返回值是什么、属于哪种请求分类 |
| [对象](/specification/fsp/objects) | 接口处理哪些容器，容器的形状、尺寸、材质、容积及状态要求是什么 |
| [系统](/specification/fsp/system) | 接口执行时要求哪些设备状态、安全围栏、异步任务和结果验证规则 |

一项操作必须同时引用自身适用的对象和系统约束。例如，加液操作不是独立于容器与设备状态的函数：它必须声明目标容器、容量约束、设备可执行状态以及完成后的结果验证。

## 请求分类

`read`、`write` 和 `invoke` 是风险分类，不是三条固定指令。具体接口由稳定 `operation_id` 标识。

| 分类 | 语义 | 最低要求 |
| --- | --- | --- |
| `read` | 读取对象、系统状态或既有结果 | 返回观测时间和数据新鲜度，不改变设备状态 |
| `write` | 修改设备状态、配置或工艺参数 | 校验可写性、范围和预期修订号，完成后回读 |
| `invoke` | 触发实际物理动作 | 下发前强制检查对象、系统和安全围栏，完成后验证物理结果 |

## 运行时接口

```text
fsp/read
fsp/write
fsp/invoke
fsp/get_task
fsp/cancel_task
```

`fsp/get_task` 和 `fsp/cancel_task` 属于系统运行机制，详细语义见[系统](/specification/fsp/system)。

## 统一请求

```json
{
  "jsonrpc": "2.0",
  "id": "request-1",
  "method": "fsp/invoke",
  "params": {
    "device_id": "device-01",
    "operation_id": "add_liquid",
    "arguments": {
      "container_id": "container-01",
      "volume_mL": 0.5
    },
    "expected_system_revision": "state-21"
  }
}
```

| 字段 | 作用 |
| --- | --- |
| `device_id` | 指定已经配置的目标设备 |
| `operation_id` | 指定 FSP 设备定义中的具体操作 |
| `arguments` | 传入该操作声明的参数 |
| `expected_system_revision` | 防止基于过期系统状态执行写入或物理动作 |

## 统一响应

```json
{
  "jsonrpc": "2.0",
  "id": "request-1",
  "result": {
    "result_type": "complete",
    "value": {},
    "system_revision": "state-22",
    "observed_at": "2026-09-02T06:00:12Z",
    "diagnostics": []
  }
}
```

`result_type` 可以是 `complete` 或 `task`。同步结果必须符合操作的返回 Schema；异步结果必须符合系统任务结构。调用方不得根据操作名称猜测未声明参数，也不得用预期状态替代实际结果。
