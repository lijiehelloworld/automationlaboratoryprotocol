## 下发方式

执行服务按 `steps` 顺序把每一步映射为 `fsp/invoke`：

```text
steps[].id         → device_id
steps[].operation  → 通过能力绑定解析为 command_id
steps[].parameters → 通过参数绑定解析为 arguments
```

设备操作是否同步或异步，由 FSP 操作定义和实际返回决定。

## 仿真输出

当前可验证证据是 `run_simulation.py` 产生的仿真报告：

```json
{
  "simulation_status": "passed",
  "verified_by": "run_simulation.py",
  "command_exit_code": 0,
  "operation_count": 6,
  "checks": [
    "调用仅使用已注册工作站函数",
    "开盖、加液、关盖和检测构成研究对象从 St 到 St+1 的状态演化",
    "强制条件失败时不提交研究对象的模拟状态"
  ]
}
```

仿真通过只证明方案在当前函数和状态模型中可运行，不证明物理设备已经执行。

## 状态提交

```text
仿真或执行成功且完成条件满足
  → 保存结果和诊断
  → 提交实际状态变化

强制校验失败、仿真阻断或设备结果未知
  → 不提交预期成功状态
  → 保留原状态或重新读取实际状态
  → 返回诊断并重新生成或修订方法
```

## 真实执行证据边界

当前 `skill_all` 没有真实 FSP 运行时的任务进度、物理执行结果和证据包样例。因此本规范不把自行构造的 `execution_id`、`evidence_id` 或设备事件当作现有产物。

设备实现 FSP 后，真实执行至少应当返回：

- 实际调用的操作和参数；
- 开始和完成状态；
- 实际对象和系统状态；
- 结果或诊断；
- 可以关联到研究对象来源记录的执行引用。

具体运行时字段以首个通过验证的 FSP 实现样例为准，再纳入非规范性示例。
