title: "编译/解释器"
description: "把设备能力和实验目标整理成程序，并根据当前状态与证据推进程序路径。"
---

语言引擎先从 FSP 获取设备能力、使用边界和约束，再由智能体（Agent）根据实验目的生成候选流程。编译/解释器把这些能力说明和候选流程整理成可检查的程序，再根据对象状态和当前证据推进程序路径。Agent 使用的动作、参数范围和对象条件必须来自 FSP 提供的能力说明。

## 能力编译

能力编译的输入是 FSP 提供的动作契约、设备能力与部署限制。语言引擎记录设备编号、能力版本、信息来源和缺失项，将它们整理为 Agent 可读的说明以及编译、仿真共用的检查规则。首次规划、能力版本变化或设备重新绑定时，都要更新这些定义。

每个函数必须绑定到明确的设备与动作版本，保留参数、单位、输入状态、必检条件、建议条件、状态效果、结果及错误说明。同名动作使用设备限定名区分，不能按名称猜测它们可以互换。

能力编译输出三类内容：供 Agent 读取的动作说明、动作与设备的绑定关系、供仿真器使用的检查规则和状态变化模型。

参数有效范围取动作契约、协议编码和适用部署限制的交集。厂家范围未知时要记录缺失，不能把软件策略上限写成厂家验证上限。

## 程序编译

Agent 根据实验目的、成功条件、对象初态及 FSP 提供的能力与约束生成候选流程。程序编译读取候选流程及其能力版本，输出保留动作绑定、参数、对象引用、控制结构和证据依赖。

![编译检查流程](/images/all-compiler-flow-gptimage.png)

编译时应检查流程结构、动作绑定、参数类型、单位和对象依赖。未登记的动作、不支持的结构以及无法确定的调用必须返回诊断，注明出错步骤和原因。

## 程序解释

解释阶段沿程序结构运行，保存变量、对象引用、分支结果和循环次数。每遇到一个设备动作，就求出具体参数：验证阶段交给仿真器做计算与校验；真实运行阶段将已验证、可确定的任务段交给执行器。执行器负责解析任务、读取 FSP 最新状态并确认可用设备，再向 FSP 下发。

条件读取的观测要关联对象、任务、时间和有效性。值为未知、过期或属于其他样品时，应返回“等待证据”或诊断。不能把未知当成假，也不能为了继续运行而虚构测量值。

仿真中的假设输入只用于覆盖相应分支。一次仿真走过一条路径，不能证明其他分支全部正确；测试条件程序时应分别提供不同观测，并记录覆盖了哪些路径。

## 有界循环与未收敛

循环处理逻辑如下。检测动作与处理动作都必须来自能力注册表：

```python
def interpret_loop(body, observe, guard, max_iterations):
    for iteration in range(max_iterations + 1):
        evidence = observe()
        require_current_evidence(evidence)
        if not guard(evidence):
            return {"status": "converged", "iterations": iteration}
        if iteration == max_iterations:
            return {"status": "not_converged", "evidence": evidence}
        body()
```

未收敛是正常的可报告结果，不能自动扩大最大次数，也不能把最后一次处理成功当成实验目标达标。

## 并行与保护区间

并行分支分别记录读取和修改的对象状态。汇合前检查状态修改与步骤依赖是否冲突；存在冲突时应返回诊断。实际调度还须满足设备和资源互斥要求。

保护区间要求指定操作连续占用所声明的资源。正常结束或异常中断时，应确认设备完成或停止状态后释放资源，并保留已经发生的样品变化。

## 简化策略

可以折叠纯常量表达式、删除确定不会执行的常量分支、去掉空语句。每次修改都要保留源码位置映射并重新检查、重新仿真。

默认保留设备调用顺序、次数、对象和参数。合并两次加液、删掉暂未使用的输出或重排操作都可能改变实验含义；只有动作契约明确允许且重新验证通过时，才能采用这些变换。诊断改写也必须有次数上限，不能一直生成直到偶然通过。

动作绑定检查逻辑：

```text
根据设备编号、动作名称和契约版本查找动作定义
若未登记该动作：返回诊断
检查必填参数和允许提供的参数
检查参数类型、单位、范围及参数之间的约束
检查对象引用和前置条件
若检查失败：返回出错步骤、参数及原因
否则：保存动作绑定、参数和契约版本
```

## 从程序到执行计划

程序中的对象及操作结构与执行后端的传输格式分开维护。生成执行计划时，将动作映射到 `action/params`，对象映射到 `containers`，设备与对象的预期版本映射到 `expected`。版本、完成条件和源码位置等审计资料应另行关联到计划，不能添加数据格式不允许的字段。

生成顺序执行计划时，步骤顺序和参数必须已经确定。依赖后续测量的条件或循环，应等待相应证据后再解释。条件分支只生成满足条件的路径；并行步骤应保留依赖和资源要求，不支持时返回诊断。

编译/解释器可以把决策前已经确定的一段步骤交给执行器，等该段结束并取得有效观测后，再选择和生成下一段。每段拥有独立幂等键，同一段重试复用原键。

生成新段后，必须依据新参数和当前对象状态重新检查并仿真。实现不支持的控制结构必须返回诊断。

仿真发现问题时，Agent 收到具体步骤、违反的约束及计算结果，修订后重新进入编译/解释和仿真。执行器发现原设备不可用，需要更换设备或调整流程时，也应回到这一过程；候选设备需要重新绑定能力并验证，不能仅替换设备编号。

编译完成只表示得到可验证程序，解释完成只表示得到当前证据下的程序路径；进入执行前还要完成[仿真](/docs/specification/engine/simulator)和[运行时校验](/docs/specification/engine/executor)。

## 流程检查与解释示例

| 处理逻辑 | 示例行为 |
| --- | --- |
| 动作绑定 | 根据设备和动作查找能力定义，检查参数和对象角色；未登记动作返回诊断 |
| 条件分支 | 先检查两个分支的结构，运行时依据有效观测只选择一条路径 |
| 有界循环 | 每轮读取更新后的状态，达到条件即结束；超过规定次数返回未收敛 |
| 证据缺失 | 条件值未知时停止解释，返回缺失证据的步骤 |
| 任务分段 | 向执行器交付当前已确定的步骤，取得后续观测后再解释下一段 |

对应实现见 [编译/解释逻辑](https://gitcode.com/mimedal/all/blob/main/examples/language_engine/compiler.py) 和 [共享动作检查](https://gitcode.com/mimedal/all/blob/main/examples/language_engine/model.py)。[验证用例](https://gitcode.com/mimedal/all/blob/main/tests/test_language_engine.py)覆盖动作缺失、参数越界、分支选择、未知条件和循环未收敛。
