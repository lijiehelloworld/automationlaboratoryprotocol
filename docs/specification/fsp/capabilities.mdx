想直接看代码，可以先读[动作契约、能力门控与 Adapter](/docs/specification/device-integration/python-example)。其中的加液例子分别展示动作定义、执行前检查和设备适配。

## 先分清三个问题

能不能执行一项操作，需要分别回答下面三个问题。文档里写了“支持加液”，不代表设备已经接好，也不代表现在就能加液。

| 要回答的问题 | 需要说明什么 | 什么时候更新 |
| --- | --- | --- |
| 这项操作是什么意思？ | 操作名称和版本、参数、结果、容器要求、启动条件、完成条件 | 操作含义或数据格式改变时 |
| 这台设备能不能做？ | 对应哪个操作、是否已实现、参数限制及其依据、配置和验收是否完成、能读回哪些状态、能否停止 | 程序、配置、标定或验收结果改变时 |
| 现在能不能做？ | 是否连接、当前状态、设备和容器是否被占用、状态是什么时候读取的、为什么不能执行 | 读取到新状态或任务状态改变时 |

## 操作定义怎样对应到具体设备

这里把一项操作的参数、结果和执行规则合称为“操作契约”。把这份定义对应到具体设备的代码，称为“绑定”。

**CAP01**：在同一套契约的命名范围内，`operation_id` 和 `contract_version` 共同确定操作含义。不同设备使用同名同版本的契约时，参数含义、单位和完成要求必须相同。来自不同命名范围的同名操作，不能直接当成同一项操作。

**CAP02**：绑定必须明确是哪台设备实现哪项操作。批量注册时，应先检查全部内容，通过后一起生效。有重复绑定、定义冲突或缺少实现时，整批失败，不能只留下其中一部分可用。找不到目标设备的实现时，必须报错，不能换用另一台设备的同名操作。

设备可以使用比契约更严格的参数范围，也可以补充标定信息和测量限制，但必须写明依据，并更新设备定义版本。不能擅自扩大范围、改变单位、增加必填参数或降低完成要求。

例如，接口只知道“命令已收到”，就不能把它接到要求“液体已加入且体积已核验”的操作上。它应使用另一份明确说明只能确认命令回执的操作定义。

换一台设备执行时，必须重新检查容器位置、参数范围、资源占用、配置和完成证据。操作名称相同，不代表原计划可以原样执行。

## 执行前要检查什么

**CAP03**：必须同时确认硬件支持、代码已实现、部署已授权、配置已完成，以及当前现场条件允许执行。不能只返回一个 `available`，却不说明不可用的原因。

| 情况 | 应怎样说明 | 怎样处理 |
| --- | --- | --- |
| 硬件不支持 | 不列为可执行操作；可以说明为什么不支持 | 拒绝，不自动换设备 |
| 声明支持，但缺少实现代码 | 说明配置或程序有误，不能标为已实现 | 拒绝，修复后再试 |
| 已实现，但配置或验收没完成 | 保留操作说明，标记 `ready: false` 并写明原因 | 拒绝，先完成配置或验收 |
| 设备正在忙，或容器被占用 | 说明当前占用情况，不删除能力声明 | 拒绝，或按已公布的规则排队 |
| 不知道当前状态，或读取结果已过期 | 说明需要重新读取哪些状态 | 相关动作暂不执行 |

同一项能力下面可能有多个操作，要分别检查它们是否实现、是否通过验收。检查函数和参数是否匹配，只能发现代码结构问题，不能证明每个动作分支都可用，也不能证明设备连接和真实动作正常。

## 能力描述示例

以下为能力描述片段，字段不属于一次操作的三段请求：

```json
{
  "device_id": "device-01",
  "definition_revision": "12",
  "operations": [{
    "operation_id": "add_liquid",
    "contract_version": "1",
    "implemented": true,
    "ready": false,
    "readiness_reason": "现场体积核验尚未完成",
    "limits": [{
      "parameter": "volume_mL",
      "minimum": 0.05,
      "maximum": 0.8,
      "unit": "mL",
      "source": "deployment_policy",
      "basis": "经审阅的部署限值记录"
    }],
    "completion_scope": "sample_effect",
    "required_evidence": ["dispensed_volume"],
    "cancellation_supported": false
  }]
}
```

`implemented` 表示代码已实现，需要有检查记录；`ready` 表示配置和验收满足要求，需要有对应依据。两者都不表示设备现在空闲。实现必须提供程序能读取的字段定义，写清类型、必填项和版本。

## 给规划程序和 AI 阅读的设备说明

**CAP04**：给规划程序使用的文档、工具 Schema 或 Function Skill，应从同一份操作定义和已检查的设备定义生成，避免各写一份、内容不一致。

生成的说明必须注明操作版本、设备定义版本、生成时间和来源摘要。它只反映生成时的信息；真正执行前，仍要重新查询设备状态。

限制来自操作定义、厂商规格、标定结果还是部署要求，要分别写清。不能在生成说明时补出没有依据的能力或验收结论。连接地址、密码等私密信息由运行环境保存，不放进这些说明。

相同输入应生成相同的主要内容。生成时间等每次变化的信息应单独处理，以便比较内容有没有变化。

## 修改定义时怎样处理版本

协议版本、操作契约版本、设备定义版本、对象和系统状态版本，分别记录不同内容的变化，不能混用。

实现必须说明支持哪些协议版本、旧字段怎样转换。不认识的版本必须拒绝，不能猜测着执行。字段位置、单位或“成功”的含义改变时，应使用新版本，或提供明确的转换规则；转换后仍要做完整检查。

新增字段不能改变旧字段的含义。请求参数或安全条件中出现未声明字段时，应拒绝；只有定义中明确允许扩展的位置，才能接受扩展字段。
