Function State Protocol（FSP，函数状态协议）连接 ALL 语言引擎和设备仪器接口。规划时，FSP 向语言引擎提供设备能力、使用边界和约束；下发前，FSP 提供当前设备与对象状态；执行时，FSP 接收执行器下发的任务，检查条件、调用设备并返回实际结果。

## 与语言引擎怎样配合

1. **提供能力和约束**：语言引擎查询设备已实现的动作、参数范围与单位、适用对象、使用条件、资源限制、结果和完成证据。FSP 保留这些信息的来源、版本和未知项。
2. **支持流程生成与仿真**：Agent 根据实验目的和上述信息生成流程；编译/解释器整理流程，仿真器计算与校验，诊断反馈给 Agent 修订。这个过程使用能力与模型说明，不触发真实设备动作。
3. **提供当前状态**：执行器在每段任务下发前重新查询 FSP，确认设备在线、空闲或可分配，且对象、安全、权限和资源条件满足。
4. **执行并返回证据**：FSP 收到任务后，通过动作契约检查、能力门控和转发器调用设备。准备执行每个动作时再次核对实时条件、取得资源，并把实际结果、对象变化和任务状态返回执行器。

查询得到的可用状态不是资源预约。设备可能在查询后被其他任务占用，最终放行以 FSP 执行动作前的检查和资源获取结果为准。

## 服务实现

FSP 服务的具体实现由三部分组成：

1. **动作契约**：定义动作的含义、参数、前置条件、结果和完成证据；
2. **能力门控**：确认目标设备硬件支持、代码已实现、配置已就绪，且当前条件允许执行；
3. **转发器**：把通用动作转成具体设备命令，再把驱动返回值转成通用结果。

FSP 对设备仪器接口提出三个维度的内容要求：**操作、对象、系统**。厂商接口必须能够说明做了什么、作用于什么对象，以及设备和任务处于什么状态。这三个维度不是 FSP 服务的三个执行模块，也不是要求厂商建立三套独立接口。

## FSP 服务的执行顺序

```text
上层函数调用
  → 动作契约：解析动作和校验参数
  → 能力门控：选定设备并检查是否允许执行
  → 转发器：转换单位、坐标和命令，调用驱动
  → 设备仪器接口：提供操作、对象、系统三个维度的实际信息
  → FSP 服务：按契约判断成功、失败或结果未知
```

动作契约通过不代表可以下发；能力门控通过也不代表设备已经完成动作。只有取得契约要求的实际结果和完成证据，才能返回成功。

## 设备仪器接口必须覆盖的三个维度

| 维度 | 请求要表达 | 返回要表达 |
| --- | --- | --- |
| [操作](/docs/specification/device-integration/operations) | 动作标识、参数、版本和执行前条件 | 是否执行、实际参数、结果、诊断和完成证据 |
| [对象](/docs/specification/device-integration/objects) | 相关容器、样品、角色、位置和执行前状态 | 实际变化、当前状态、观测时间和对象版本 |
| [系统](/docs/specification/device-integration/system) | 设备状态、安全限制、资源、幂等键和执行模式 | 实际设备状态、安全检查、任务、资源占用和注意事项 |

厂商接口的操作调用、状态查询、结果回调或事件通知可以采用不同方法，但合在一起必须完整覆盖这三个维度。接口不能只告诉调用方“命令已收到”，却不提供对象变化和设备或任务状态。HTTP、CLI、MCP、RPC 或厂商 SDK 都可以作为承载方式；FSP 不规定 URL、工具名、命令名或 SDK 方法名。
