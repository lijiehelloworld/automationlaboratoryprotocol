Function State Protocol（FSP，函数状态协议）不定义固定请求 URL、调用命令或传输协议。HTTP、CLI、MCP、RPC 和厂商 SDK 都可以承载符合 FSP 的设备接口。

FSP 规定的是接口规则：每项设备操作的说明、请求和响应都必须完整表达对象、操作和系统三个部分。

![FSP 函数状态协议架构](/images/fsp-protocol-architecture.png)

## 三段接口模型

| 维度 | 请求必须说明 | 响应必须说明 |
| --- | --- | --- |
| [对象](/docs/specification/fsp/objects) | 目标容器、当前容器状态、样品状态和容量条件 | 容器实际状态、状态变化和对象版本号 |
| [操作](/docs/specification/fsp/operations) | 操作标识、参数、范围、枚举和操作执行前条件 | 是否执行、实际参数、执行结果和诊断 |
| [系统](/docs/specification/fsp/system) | 设备预期状态、安全限制、执行模式和任务条件 | 当前设备状态、安全检查、任务进度和注意事项 |

这三段不是独立接口，而是同一操作的完整契约。设备或适配层可以采用任意调用方式，但不得省略任一维度。

## 不依赖调用方式的操作定义

```json
{
  "device_id": "device-01",
  "object": {},
  "operation": {"operation_id": "add_liquid"},
  "system": {}
}
```

同一契约可映射为：

| 调用方式 | 实现形式 |
| --- | --- |
| HTTP | 请求体携带三段字段，响应体返回对象、操作、系统三部分结果 |
| CLI | 命令参数或输入文件表达三段字段，标准输出或结果文件返回对象、操作、系统三部分结果 |
| MCP | 工具输入 Schema 表达三段字段，工具结果返回对象、操作、系统三部分结果 |
| RPC / SDK | 方法参数对象和返回对象表达三段字段 |

FSP 不规定这些调用方式的路径、方法名、命令名或 SDK 方法名。

上例仅展示字段归属，不是可直接执行的加液请求。完整请求还需要受影响容器、版本、参数、幂等键和安全条件，见[接口定义](/docs/specification/device-integration/overview)。

## 从“支持操作”到“确认完成”

实现必须分清五件事：操作有没有定义、这台设备有没有实现、现在能不能执行、命令有没有发出、结果有没有达到要求。前一步成立，不代表后一步也成立：

```text
契约与设备绑定 → 现场条件检查 → 持久化受理与资源预留
→ 下发动作 → 收集完成证据 → 更新可确认事实与任务状态
                          ↘ 证据不足：unknown／等待确认 → 核实
```

本规范使用“必须／不得”表示强制要求，“应”表示有理由偏离时必须说明的建议，“可以”表示可选能力。条款编号用于[符合性验证](/docs/specification/conformance)，不表示仓库已提供相应运行时实现。

- [操作定义与设备能力](/docs/specification/fsp/capabilities)：操作怎样对应设备，以及生成的设备说明能用于什么。
- [任务状态与异常恢复](/docs/specification/fsp/lifecycle)：状态转换、幂等、资源、取消与重启。
- [操作](/docs/specification/fsp/operations)：完成范围、实测结果和证据要求。
