## ALL 和 FSP 是什么关系？

ALL 语言引擎从 FSP 读取设备能力、使用边界和约束，通过 Agent 根据实验目的生成流程，再组织编译/解释、仿真和执行。FSP 提供设备信息、接收任务并执行动作；其服务实现由动作契约、能力门控和转发器组成。

## Agent、仿真器和执行器如何配合？

Agent 先生成候选流程，编译/解释器整理和检查步骤，仿真器计算预测变化并检查约束。问题反馈给 Agent，修订后重新仿真。通过后，执行器解析任务，下发前向 FSP 查询最新状态，确认当前设备可用，再交给 FSP 执行。实际结果回到执行器，供后续步骤判断使用。

## 已经读取过设备能力，为什么下发前还要查询？

能力说明记录设备能做什么，实时状态反映此刻能否执行。规划结束后，设备可能离线、被占用或发生状态变化。执行器要在下发前重新确认；FSP 还要在动作执行前取得资源并再次检查。变化影响原流程时，需要重新规划和仿真。

## 设备必须原生实现 FSP 吗？

不需要。现有 HTTP API、CLI、MCP 工具、厂商 SDK、RPC、消息接口或驱动都可由转发器映射为 FSP。

## 为什么厂商接口要包含操作、对象和系统？

这是 FSP 对设备仪器接口提出的三方面内容要求：操作说明做什么、参数和结果；对象说明操作哪个容器或样品及其状态变化；系统说明设备状态、安全限制、任务和资源。三者不是三个独立服务，也不要求厂商建立三套接口，但厂商接口提供的调用、查询、回调或事件必须能够完整给出这三方面信息。

## 异步任务属于哪个模块？

异步任务属于 FSP 系统部分。操作受理后可返回任务标识；后续状态、结果和取消信息通过系统任务返回。

## 仿真通过是否等于实验成功？

不等于。仿真只说明步骤通过了已定义的检查，不证明真实设备或样品会达到预期。执行时仍要检查容器和设备状态，并按实际测量和检查结果判断是否成功。
